# Reproducible agent jar: what changed and what it does to the jar

Goal: two builds of the same source produce a byte-identical `newrelic-agent/build/newrelicJar/newrelic.jar`, so their hashes can be compared.

All measurements below compare a jar built from the code **before** these changes (`base1.jar`) with a jar built **after** (`u1.jar`). Both were built with `./gradlew clean jar --parallel` on one machine (JDK 8, Corretto 8.332), at the same agent version (`9.6.0-SNAPSHOT`) and the same git SHA.

## 1. Code changes

| # | File | Change |
|---|------|--------|
| 1 | `build.gradle` (root, inside `allprojects {}`) | Every `AbstractArchiveTask` (jar, shadowJar, zip, tar, sourcesJar, javadocJar, and so on) in every project now sets `preserveFileTimestamps = false` and `reproducibleFileOrder = true`. They also set `filePermissions { unix("644") }` and `dirPermissions { unix("755") }`, so the permission bits in the jar no longer depend on the build machine's umask. |
| 2 | `buildSrc/src/main/java/com/nr/builder/PropertySerializer.java` | `PointcutClasses.properties` is still written with `Properties.store()`, but it is called with no header comment and the output is captured first. Every line starting with `#` (the only one is the timestamp) is dropped, and the `#Automatically generated by PropertySerializer` header is written explicitly. The header text, key order and class order are unchanged. |
| 3 | `buildSrc/src/main/java/com/nr/builder/GitUtil.java` | New method `commitDate(Project)`. It uses `SOURCE_DATE_EPOCH` if set, otherwise the HEAD commit time (`git log -1 --format=%ct`), otherwise the current time. The result is formatted `EEE MMM dd HH:mm:ss zzz yyyy` in **UTC**. A non-integer `SOURCE_DATE_EPOCH` fails the build. The existing `sha()` and the new method now share a private `firstLineOfGitOutput()` helper instead of each running git themselves. `sha()` behaves the same, including its error handling; only the exit-status message is built from the arguments (`git rev-parse HEAD exited with status N`, as before). |
| 4 | `newrelic-agent/build.gradle` (manifest) | `Built-Date` changed from `new Date()` to `GitUtil.commitDate(project)`. For `DEV` versions it is still the literal `DEV`. `Built-By` is **unchanged** (`System.getProperty('user.name')`). |

## 2. Every difference in the produced jar (measured)

Overall:

| Item | Before | After |
|------|--------|-------|
| File size | 41,324,508 bytes | 41,324,289 bytes (219 bytes smaller) |
| Top-level entries | 15,074 | 15,074 |
| Entries including those inside nested jars | 33,865 | 33,865 |
| Entry names | | identical set |
| Top-level entry order | | identical |
| Content of the 441 `instrumentation/*.jar` files | | byte-identical, 441 of 441 |
| Content of all `.class` files and other resources | | identical (verified for every entry, including inside nested jars) |
| Compression method, external attributes, extra fields, comments, flag bits | | identical for every entry |

The only differences are the following. Anything not listed here was compared and found identical.

### 2.1 `META-INF/MANIFEST.MF`: one line changes

```
< Built-Date: Fri Nov 06 14:37:17 PST 2026
> Built-Date: Fri Nov 06 17:19:14 UTC 2026
```

- **Value:** the time the build ran, now the time of the HEAD commit (or `SOURCE_DATE_EPOCH`).
- **Time zone:** the build machine's local zone (`PST`), now always `UTC`.
- **Format:** the same pattern as `Date.toString()`.
- **`Built-By`:** unchanged. It is still the real user name, so builds by different users still differ.
- **`X-Git-SHA`:** unchanged. It is still the real commit SHA.
- **`Build-Id`:** unchanged. It is still `None` unless `BUILD_ID` is set.
- **Other manifest attributes:** unchanged.

How the agent uses it: `RPMService` reads `Built-Date` as a plain string through `AgentJarHelper.getBuildDate()` and sends it as the `build_date` setting when it connects. It is not parsed anywhere I found, so the format change should not break anything. Anything on the New Relic side that displays or parses `build_date` was not checked.

### 2.2 `PointcutClasses.properties`: one line removed

Before: `Properties.store()` wrote a header comment, then a comment with the current time, then the entries.

```
#Automatically generated by PropertySerializer
#Fri Nov 06 14:37:28 PST 2026
<entries>
```

After: the same, without the timestamp line.

```
#Automatically generated by PropertySerializer
<entries>
```

- **Diff:** a `diff` of the old and new file shows exactly one change, the removed `#Fri Nov 06 ...` line. The entries are the same, in the same order.
- **Reader:** `Annotations.buildAnnotatedClasses()` reads the file with `Properties.load()`, which ignores comment lines.
- **Not tested at runtime:** I did not start an agent with the new jar to confirm it loads.
- **Ordering is not forced:** entry order and class order still come from `Properties` and the Reflections multimap. On one machine they were identical across builds. A build from a fresh checkout in another directory also gave an identical file. The order does differ between JDK families (see section 4a).
- **Layout independence:** the code does not assume where the timestamp is. Entries are class names, which never start with an unescaped `#` (`Properties` escapes a leading `#` in a key), so every line starting with `#` is a comment and is dropped wherever the JDK writes it. It was checked by building on JDK 8, 17 and 21, which cover the three `Properties.store()` behaviors (`Hashtable` order, `ConcurrentHashMap` order, sorted). On each, `PointcutClasses.properties` matched the earlier build and contained exactly one `#` line, the header. The one case this does not cover is a future JDK writing the timestamp on a line that does not start with `#`. `Properties.store()` is specified to write it as a comment, so I did not add a check for that.

### 2.3 Zip entry timestamps

Measured across all 33,865 entries (including those inside nested jars): the modification time changed on **11,071** entries. Only metadata changed. The content of those entries is identical.

- **Before:** each entry had the modification time of the source file or build artifact. The most common values were `1980-02-01 00:00:00` (14,891 entries), `2026-07-01 09:46:30` (1,488) and `2023-01-14 13:21:04` (1,307), plus the build time for `META-INF/MANIFEST.MF` and similar entries.
- **After:** all entries Gradle creates use the fixed value `1980-02-01 00:00:00` (25,962 entries). The `2023-01-14 13:21:04` entries (1,307) are unchanged, because they are copied unmodified from dependency jars. The remaining entries keep their dependency jars' original timestamps.
- **What this affects:** anything that reads the modification time of entries inside `newrelic.jar`. The agent's own code does not appear to depend on this, but I only checked the `Built-Date` and `PointcutClasses` usages.

### 2.4 Five nested jars: new entry order and timestamps

These jars are embedded at the top level of `newrelic.jar`:

- `agent-bridge.jar`
- `agent-bridge-datastore.jar`
- `newrelic-api.jar`
- `newrelic-weaver-api.jar`
- `newrelic-weaver-scala-api.jar`

For each one:

- The set of entries is identical, the content of every entry is identical, and the entry count is identical.
- The entry **order** inside all five changed.
- Entry timestamps changed from the build time of that jar (for example `2026-10-01 15:56:12`) to `1980-02-01 00:00:00`.
- Their byte sizes are the same as before.
- Because the bytes of these jars changed, their SHA-256 changed even though they contain exactly the same classes.

The 441 `instrumentation/*.jar` files were already reproducible before this change (`instrumentation/build.gradle` already set the same two options), so they are unchanged.

### 2.5 Entry permissions

Zip entries record Unix permission bits. Before these settings, files the build created took their permissions from the build machine's umask.

- **Under the default umask (`022`), nothing changes.** The jar has 26,882 files, all `0644`, and 6,983 directories, all `0755` (counting entries inside nested jars). There are no executable files, so forcing `644` and `755` removes nothing intentional. The permission bits of every entry were identical before and after.
- **Under other umasks, the old build differed.** With `umask 077` the bits changed on 447 entries (`0644` to `0600`). With `umask 000` they changed on the same 447 entries (`0644` to `0666`). The affected entries were the files the build creates, such as `PointcutClasses.properties` and the embedded jars. Entries copied from dependency jars were not affected.
- **After the change**, `umask 022`, `077` and `000` all produce the same jar.
- **The production jar already has these permissions.** The agent jar published by the GitHub workflows (`newrelic-agent-9.5.0.jar`) has 14,409 files all `0644` and 663 directories all `0755`, with every entry created on Unix. A local build with these changes has 14,412 files all `0644` and 662 directories all `0755`. Across the 15,066 entries both jars contain, there are no permission differences. The fixed values match what the production build produces under its normal umask, so published artifacts keep the same modes. This compares only the top-level entries of the two jars (the 26,882 and 6,983 counts above also include nested jars). The two jars were probably built from different commits, since a few class entries differ. The published `newrelic-java-9.5.0.zip` (the `dist` bundle) was compared the same way: it has the same 10 entries as a local `:newrelic-java:dist` build, with one directory `0755` and nine files `0644` in both, so no permission differences. Its entries carry real timestamps (2026-09-23) where the local build has 1980-02-01, and `newrelic.yml` is listed in a different position because of `reproducibleFileOrder`. The published `newrelic-api-9.5.0.jar` was compared too: it has the same 106 entries as the local `newrelic-api` jar, with 101 files `0644` and 5 directories `0755` in both and no permission differences (production timestamps are real build times, local are 1980-02-01). The published `newrelic-agent-9.5.0-sources.jar` and `newrelic-agent-9.5.0-javadoc.jar` were compared with local builds as well. In both, every shared entry has identical permissions (sources: 968 files `0644` and about 100 directories `0755`; javadoc: about 1,250 files `0644` and about 100 directories `0755`), all created on Unix. The entry lists differ by a few entries, consistent with the production jars being built from a different commit (9.5.0 versus the local 9.6.0-SNAPSHOT). Production timestamps are real build times and local ones are 1980-02-01. The jars nested inside the zip were not checked against production.

## 3. Effects outside the agent jar

Change 1 applies to **all** archive tasks in **all** projects, not only the agent jar. I did not diff these other outputs, so this section is based on the code change, not on measurement:

- Other jars built by Gradle (`newrelic-api`, `agent-bridge`, `sourcesJar`, `javadocJar`, test jars and others) will get `1980-02-01` entry timestamps and a deterministic entry order.
- Zip distributions, such as the `newrelic-java` bundle, will behave the same way.
- Published Maven artifacts will have those timestamps too. Their content is unchanged.
- Gradle's up-to-date checks and build cache keys may treat archive tasks as changed once, on the first build after this change.

## 4. What this does and does not guarantee

Verified (JDK 8, macOS):

| Scenario | Result |
|----------|--------|
| 2 clean builds, `SOURCE_DATE_EPOCH` unset | identical, SHA-256 `15cf8c81…1beb5` |
| 2 clean builds, `SOURCE_DATE_EPOCH=1700000000` | identical, SHA-256 `e7e66f2b…ee85a8`, with `Built-Date: Tue Nov 14 22:13:20 UTC 2023` |
| 2 clean builds, one in the original checkout and one in a fresh `git worktree` in a different directory (git-ignored `lib/` jars copied over), `SOURCE_DATE_EPOCH` unset | identical, SHA-256 `15cf8c81…1beb5` |
| 3 clean builds with `umask 022`, `077` and `000`, same commit, `SOURCE_DATE_EPOCH` unset | identical, SHA-256 `3885f674…` |
| Timezone `Asia/Tokyo` with locale `tr_TR.UTF-8`, and JVM options `-Duser.language=tr -Duser.country=TR -Dfile.encoding=ISO-8859-1`, against a control build of the same commit | identical to the control |
| `SOURCE_DATE_EPOCH=abc` | build fails with a message naming the variable |

Not covered:

- **Different `Built-By`:** a build by another user, or on another machine with another `user.name`, produces a different jar. `Built-By` was deliberately kept real.
- **Different commit:** a new commit changes `X-Git-SHA` and `Built-Date`, even if no code changed. To compare across commits, pin `GITHUB_SHA` and `SOURCE_DATE_EPOCH`.
- **Different `BUILD_ID`:** this goes into the `Build-Id` attribute.
- **Uncommitted changes:** these change the jar content but not `Built-Date`, because the date comes from HEAD.
- **Different JDKs:** see section 4a. The JVM running Gradle must be the same major version family, and every toolchain compiler must be the same exact patch release. A different patch release can change class files.
- **Different OS:** only macOS was tried.
- **No git and no `SOURCE_DATE_EPOCH`:** `Built-Date` falls back to the current time with an error message, and the build is not reproducible.
- **Release builds:** `Built-Date` is now the commit time, not the actual build time. This applies to every build, not only local ones.
- **Not tested:** the unit tests, the functional tests, running an agent from the new jar, a build from a source tarball with no `.git`, and a build on a different machine. A fresh checkout skips instrumentation modules whose git-ignored `lib/` jars (WebLogic, WebSphere, Oracle, Resin) are missing, so it produces a different jar unless those files are present.

## 4a. JDK requirements

Two JDK inputs affect the jar. For jars to match, both must be the same on every build machine.

**1. The JVM running Gradle: same major version family.** Measured with otherwise identical builds on macOS: JDK 8 gave one hash, JDK 11 and 17 (several vendors each) gave a second, and JDK 19, 20 and 21 gave a third. The vendor and patch version did not matter. Everything other than ordering was identical:
- Manifest attribute order (443 manifests, including those in nested jars). `java.util.jar.Attributes` is a `HashMap` on JDK 8 and a `LinkedHashMap` on JDK 9 and later.
- Entry order in `PointcutClasses.properties` (`Hashtable` on JDK 8, `ConcurrentHashMap` on 9 to 17, sorted on 18 and later).

`CLAUDE.md` requires JDK 8 for the build, so builds on JDK 8 are comparable with each other.

**2. The compilers behind the Java toolchains: same exact JDK patch release, not just the same vendor and major version.** The build compiles most modules with a fixed JDK 8 toolchain, but 49 instrumentation modules (33 on Java 17, 15 on Java 11, 1 on Java 21) and the `java11` source set of `newrelic-agent` use a toolchain for another version. Gradle toolchains can select only the language version and the vendor, so which patch release gets used depends on what is installed on the machine.

Different patch releases of javac can generate different bytecode for the same source. Found with `instrumentation/spring-webflux-6.1.0`: building it with `vendor = JvmVendorSpec.AMAZON` (Corretto 17.0.13) and without (the default Temurin 17) gave different jars (`470fc0a6…` vs `1df816bf…`). One of 31 classes, `AbstractServerResponse_Instrumentation.class`, differed. The bytecode differs, not only the constant pool order. String concatenation compiled to one `invokedynamic makeConcatWithConstants(HttpMethod)` with Corretto 17.0.13, and to `String.valueOf(Object)` followed by `makeConcatWithConstants(String)` with the other compiler.

Compiling one small snippet with each JDK 17 on the machine showed that the vendor does not matter and the javac version does:

| javac | String concatenation of an `Object` |
|-------|-----------------------------------|
| 17.0.4.1 Temurin, 17.0.9 GraalVM, 17.0.12 GraalVM, 17.0.13 Temurin, 17.0.13 Corretto | `invokedynamic` directly on the `Object` |
| 17.0.14 Zulu, 17.0.15 Temurin, 21.0.5 Temurin | `String.valueOf` first, then `invokedynamic` on the `String` |

The behavior changed between 17.0.13 and 17.0.14. I did not look up the corresponding JDK bug. Java 11 did not show a difference in the earlier test (Temurin 11.0.25 against Zulu 11.0.26), but only because the code compiled there did not hit a codegen change. That does not mean 11 is safe in general.

**Requirement.** To compare jars, build them on machines with the same JDK 8, the same JDK for each other toolchain version in use (11, 17, 21), and the same patch release of each. A different patch release of any of them can change class files in the affected modules.

Ways to enforce it:
- **GitHub Actions (the production build) already does the pinning.** `.github/actions/setup-environment/action.yml` installs Temurin 8, 11, 17, 21, 25 and 27-ea with `actions/setup-java`, then passes `-Porg.gradle.java.installations.auto-detect=false -Porg.gradle.java.installations.fromEnv=JAVA_HOME_8_X64,JAVA_HOME_11_X64,...` to Gradle through `GRADLE_OPTIONS`. Gradle can therefore see only one JDK per major version, so the vendor can't vary. Workflows that build the agent (`X-Reusable-BuildAgent.yml`, `publish_release.yml`, `publish_main_snapshot.yml` and others) all use this shared action and `$GRADLE_OPTIONS`.
- **CI sets `SOURCE_DATE_EPOCH` to the HEAD commit time.** The same action has a step, "Set SOURCE_DATE_EPOCH to the HEAD commit time", that runs `echo "SOURCE_DATE_EPOCH=$(git log -1 --format=%ct)" >> $GITHUB_ENV`. Every workflow that uses the action then builds with the variable set. `GitUtil.commitDate()` already falls back to `git log -1 --format=%ct`, so the value is the same as before; the step makes it explicit and means the build no longer depends on `git` running inside Gradle. On pull-request events `actions/checkout` checks out a merge commit, so HEAD is that merge commit, whose time changes whenever the PR or its base branch changes. Builds from `main` or a release tag use the real commit. I have not run this in a workflow.
- **Still not pinned in CI: the patch release.** The action asks `setup-java` for `17`, `21` and so on, not an exact version such as `17.0.15+6`. As I understand `setup-java`, that resolves to whatever Temurin 17 patch release is available on the runner when the job runs, so two builds run at different times can use different patch releases (the case that produced different jars for `spring-webflux-6.1.0`). `27-ea` is an early-access build and moves even more. I have not checked how `setup-java` resolves versions on `ubuntu-24.04` runners. To pin it fully, give `setup-java` exact versions.
- **A module-level `vendor = JvmVendorSpec.AMAZON` can't be satisfied in CI.** With auto-detect off and only Temurin installed, there is no Amazon JDK for Gradle to select. I have not run this in CI, so I can't say whether it fails the build or something else happens. Don't commit that line.
- **The Gradle JVM in CI.** As I understand `setup-java`, when several versions are listed the last one becomes the default `JAVA_HOME`. Here that is `8`, which matches the JDK 8 requirement above. I did not confirm that in a workflow run.
- **Local builds.** Outside CI, pin the installed JDKs the same way: `org.gradle.java.installations.auto-detect=false` and `org.gradle.java.installations.paths=...` in `gradle.properties`.
- Optionally, `-XDstringConcat=inline` (a hidden javac option) makes concatenation codegen the same for 17.0.13 Corretto, 17.0.15 Temurin and 21.0.5 Temurin in a snippet test (identical class, no `invokedynamic`). It would only cover this one kind of difference, would change the bytecode of every module that got it, and was not applied to the build or checked against the weaver. It is not part of the current changes.

If two jars differ and everything in section 4 matches, compare the class files with `javap -c -p` and check the JDK patch releases first.

## 5. Reverting or limiting the effect

- To keep the real build time again: change `GitUtil.commitDate(project)` back to `new Date()` in `newrelic-agent/build.gradle`. Everything else stays reproducible except `Built-Date`.
- To avoid touching other projects' archives: move change 1 from the root `allprojects {}` into `newrelic-agent/build.gradle` and the projects that feed `jarIntoJar`. That keeps the agent jar reproducible and leaves the remaining outputs as they were.
- To compare jars while ignoring `Built-Date` and `Built-By`: add a task that hashes the jar contents with those two manifest lines masked. That would work across users and machines, but it is a different hash from the file's own SHA-256.

## 6. Further recommendations from reproducible-builds.org (not applied)

Checked against https://reproducible-builds.org/docs/ (including the JVM page). Already covered above: archive timestamps and order, `SOURCE_DATE_EPOCH`, UTC and `Locale.ENGLISH` for `Built-Date`, the full (not abbreviated) git hash, file permissions, and pinning JDKs. Timezone, locale and encoding were tested and do not change the jar (section 4). A build in a different directory also matched.

Not applied:
- **`mavenLocal()` is a configured repository** (`build.gradle` and `settings.gradle`). A developer's `~/.m2` can shadow a real dependency, so two machines can resolve different artifacts. CI starts clean, so the production build is not affected. Removing it for release builds, or listing it last, would close the gap.
- **No dependency locking or checksum verification.** Gradle supports both (`--write-locks`, `--write-verification-metadata sha256`). I found no dynamic dependency versions in the core modules with a grep, but the search was not exhaustive. This adds maintenance to every dependency bump.
- **No separate build-info file.** The docs recommend recording the build environment as a sidecar next to the artifact, not inside it. It would hold the patch release of each JDK, the Gradle version, the OS, the commit and the jar's SHA-256. That would have made the `spring-webflux-6.1.0` javac difference easy to diagnose.
- **`Built-By` records the username.** The docs' first commandment says not to. It was deliberately kept, and in CI the user is constant, so it only matters when comparing builds by different users.
- **`PointcutClasses.properties` order depends on the JDK family** (section 4a). The docs' "stable order" advice would call for sorting it, but CI uses JDK 8 only and Gradle's manifest attribute order would still differ across JDK families.
- **`java.properties.date`** (a system property the docs mention for `Properties.store()`) is not available on JDK 8, so it cannot replace the timestamp handling in `PropertySerializer`. I did not check which JDK version added it.

Not tested: a jar built on macOS against one built on the Linux CI runner.
